# TraceGuard — 药品追溯码监管引擎

基于追溯码扫码记录识别**回流药**（医保结算购药被低价回收后重新流入市场）和
**假码/一码多卖**（扫一个真码、卖出多盒假药）的 Java 服务核心。

## 核心思路：不数次数，看状态机

同一盒药在流通中本来就会被合法扫 4~6 次（生产出库→批发入库→批发出库→药店入库→销售），
所以"扫码次数多"不是异常。真正的判据是**扫码环节组成的序列是否符合流通链路**。

引擎为每个追溯码维护一条按扫码时间排序的事件时间线，用生命周期状态机回放：

```
未激活 → 已生产出库 → 流通中(批发) → 零售在架 → 已售出 → (销毁)
                              ↑           │
                              └── 退供应商 ┘  └─ 患者退货(同店/窗口期内) → 回到在架
```

- 合法链路（含退货、拆零）天然通过，零告警；
- 违反状态机的事件产生告警，告警直接携带**触发事件的机构、环节、时间**——
  这就是"定位到具体哪个环节出的问题"。

## 识别规则

| 规则 | 判定 | 告警 |
|---|---|---|
| 回流药 | 已售出（尤其医保结算）的码再次出现入库/出库/退供应商扫码 | `REFLOW_DRUG` |
| 一码多卖 | 同一码两次销售；或在 A 店在架却在 B 店销售 | `CODE_REUSE` |
| 拆零超量 | 拆零累计数量 > 每盒最小单位数（如每盒 10 单位拆了 14） | `CODE_REUSE` |
| 码被复制 | 同一码在不可能的时间间隔内出现在两个地区 | `CODE_REUSE` |
| 异常退货 | 非原销售门店退货、超期退货、未售先退 | `ABNORMAL_RETURN` |
| 流向断链 | 未入库先销售、无出库记录跨机构转移等（需人工复核） | `SEQUENCE_VIOLATION` |

## 工程难点的处理

- **乱序/迟到数据**：新事件按扫码时间插入时间线后整体回放（单盒历史通常 <50 条，
  代价极小），通过 `alertedEventIds` 保证同一问题环节只告警一次，迟到数据只修正结论。
- **重复上报**：按 `eventId` 幂等去重。
- **退货**：同店、窗口期内的患者退货使状态回到"在架"，允许再次销售，不误报；
  异店退货是回收药洗白的典型手法，高危告警。
- **拆零**：按 `unitsPerBox`（每盒最小单位数）累计拆零量，卖满一盒才进入"已售出"。

## 海量数据部署架构（全省药店日增量）

```
药店/批发扫码 → Kafka(按 traceCode 分区)
                     │
              Flink KeyedProcessFunction
              (key = traceCode, 状态存 RocksDB, TTL=药品有效期)
                     │
        ┌────────────┼─────────────┐
     告警 Kafka    码画像 Doris/ES   离线复核 Spark
     → 监管平台    → 监管端查询     (全量重算/规则回测)
```

- 引擎 `TraceCodeEngine` 无状态，状态全部抽象在 `CodeStateStore` 接口后：
  单机用 `InMemoryCodeStateStore`，生产换成 Flink keyed state 或 Redis 实现即可，
  规则代码零改动。
- 按 traceCode 分区天然水平扩展；单码状态 < 1KB，亿级码 RocksDB 可承载。
- 事件时间 + watermark 处理迟到数据；离线侧每晚全量复核，兼顾实时性与准确率。

## 运行

```bash
javac -d out $(find src -name '*.java')
java -cp out com.traceguard.demo.Demo
```

Demo 覆盖 6 个场景：正常链路零告警、医保售出后回流、一码多卖、拆零超量、
合法退货再售、异店异常退货。
